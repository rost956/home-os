Нужно добавить в существующий проект полноценную вкладку **«Бензин»** для мониторинга наличия топлива на выбранных АЗС, накопления собственной истории и прогнозирования следующих поставок.

ВАЖНО: сначала полностью изучи существующий проект и его архитектуру. Не создавай параллельную архитектуру и не переписывай без необходимости существующие механизмы.

Текущий проект уже работает как домашний веб-сервис. Основной стек:

* FastAPI
* PostgreSQL
* Docker Compose
* Caddy
* PWA / существующий frontend проекта

Нужно встроить функцию в существующий интерфейс и существующий backend в стиле остальных разделов проекта.

Главная цель:

Я хочу вручную добавлять интересующие меня АЗС по адресу, выбирать конкретную найденную станцию, выбирать отслеживаемые типы топлива и после этого больше ничего не делать.

Сервис должен самостоятельно:

* регулярно получать данные;
* хранить историю;
* определять изменения наличия топлива;
* выделять предполагаемые события поставки;
* анализировать регулярность поставок;
* анализировать взаимосвязь между станциями одной сети;
* прогнозировать следующую поставку;
* показывать вероятность/уверенность прогноза;
* объяснять, на основании чего сделан прогноз.

## 1. Отслеживаемое топливо

В рамках этой функции нас интересуют ТОЛЬКО:

* АИ-95
* АИ-98
* АИ-100

92, дизель, газ и остальные виды топлива не показывать и не анализировать.

Архитектуру при этом сделать такой, чтобы список видов топлива позже можно было расширить.

## 2. Источник данных

Основной источник сейчас — `gdebenz.ru`.

Использовать доступные JSON API GdeBenz.

Известные возможности API:

* `/api/stations?lat1=&lon1=&lat2=&lon2=` — станции внутри bbox;
* `/api/nearby?lat=&lon=&radius_km=` — станции вокруг точки;
* `/api/search?q=` — поиск;
* `/api/comments/{osm_id}/recent?limit=12` — свежие комментарии конкретной АЗС;
* `/api/comments?lat1=&lon1=&lat2=&lon2=` — комментарии/отметки в области.

Из данных нас интересуют как минимум:

* ID/OSM ID станции;
* координаты;
* название;
* бренд;
* адрес;
* общий status;
* `fuels_now`;
* `last_at`;
* `confirmations`;
* `confidence`;
* `conflict`;
* `prices_now`;
* любые другие полезные поля, реально присутствующие в API.

Не доверяй заранее придуманной структуре ответа.

Сначала выполни реальные запросы к API, изучи фактический JSON и только после этого реализуй Pydantic-модели/parser.

API неофициальный и может измениться.

Поэтому обязательно создать абстракцию источника данных, например:

```python
class FuelDataProvider(Protocol):
    async def find_stations(...)
    async def get_stations_in_bbox(...)
    async def get_station_comments(...)
```

А конкретную реализацию назвать примерно:

```python
GdeBenzProvider
```

Бизнес-логика не должна напрямую зависеть от HTTP-формата GdeBenz.

В будущем должен быть возможен второй источник, например gdebenzi.ru, без переделки всей подсистемы.

Для HTTP обязательно:

* нормальный User-Agent приложения;
* необходимые Referer/headers, если требуются сервисом;
* разумный timeout;
* retry с backoff;
* обработка 429;
* обработка 5xx;
* обработка изменившегося/битого JSON;
* логирование ошибок;
* ошибка API никогда не должна превращаться в состояние «бензина нет».

При ошибке источник должен считаться временно недоступным, а последнее известное состояние сохраняться со статусом stale.

## 3. Добавление АЗС пользователем

Во вкладке должна быть кнопка:

**+ Добавить АЗС**

Пользователь вводит, например:

```text
Teboil
проспект Ветеранов, 188/1
```

или просто:

```text
проспект Ветеранов, 188/1
```

Система должна:

1. Геокодировать адрес.
2. Получить координаты.
3. Найти через GdeBenz станции рядом с координатами.
4. Отсортировать кандидатов по расстоянию.
5. Показать несколько вариантов.
6. Дать пользователю вручную выбрать нужную АЗС.
7. После выбора сохранить стабильный идентификатор станции из источника.

НЕЛЬЗЯ автоматически сохранять первый результат без подтверждения пользователя.

Карточка выбора примерно:

```text

  пр. Ветеранов, 188/1
  74 м

○ Газпромнефть
  ...
  680 м

[Выбрать]
```

После выбора спросить, какие виды топлива отслеживать:

```text
[x] АИ-95
[x] АИ-98
[x] АИ-100
```

По умолчанию выбраны все три.

## 4. Геокодирование

Для первоначальной реализации можно использовать OSM Nominatim.

Но соблюдать ограничения публичного Nominatim:

* геокодирование выполняется только по явному действию пользователя при поиске адреса;
* НЕ использовать Nominatim в background poller;
* кешировать результат адрес → координаты;
* не делать повторный запрос для уже известного адреса;
* не более 1 запроса в секунду;
* установить осмысленный User-Agent приложения;
* показать необходимую attribution OpenStreetMap в соответствующем месте UI.

URL/провайдер геокодера не зашивать глубоко в бизнес-логику.

Создать abstraction/interface геокодера, чтобы позднее можно было заменить Nominatim на Яндекс или другой provider через конфигурацию.


```text

```

Он должен корректно переживать:

## 8. Как определять состояние отдельного топлива

Нужно написать отдельную функцию нормализации ответа GdeBenz.

Исходный общий station status недостаточен.

Для каждого из `95`, `98`, `100` определять отдельное состояние.

Учитывать:

* station status;
* `fuels_now`;
* freshness `last_at`;
* confidence;
* confirmations;
* конфликт/queue;
* отсутствие свежих данных.

Очень старую отметку нельзя показывать как достоверное текущее состояние.

Ввести понятие freshness/staleness.

Порог свежести сделать конфигурируемым.

Например:

```text
FUEL_DATA_STALE_AFTER_MINUTES
```

Не делать ложный вывод:

```text
API не ответил -> топлива нет
```

Правильно:

```text
API не ответил -> последнее состояние + stale
```

## 9. Детектор поставки

Нужно автоматически определять событие предполагаемой поставки.

Простейший надёжный сигнал:

```text
достоверно unavailable
          ↓
достоверно available/low
```

Пример:

```text
18:10 unavailable
18:15 unavailable
18:20 unavailable
18:25 available
18:30 available
```

Предполагаемое окно поставки:

```text
18:20–18:25
```

`estimated_at` можно брать как midpoint:

```text
18:22:30
```

Но сохранить само окно обязательно.

Нельзя создавать высокоуверенную поставку из:

```text
unknown -> available
```

если до этого несколько часов не было данных.

Нужно учитывать:

* продолжительность разрыва между последним `unavailable` и первым `available`;
* свежесть исходных отметок;
* confidence;
* confirmations;
* повторное подтверждение состояния следующим poll;
* комментарии пользователей, если есть.

Сделать confidence события, например 0..1.

Пример:

```text
0.95:
unavailable -> available
окно 5 минут
обе отметки свежие
есть подтверждения

0.65:
окно 30 минут
мало подтверждений

0.20:
после неизвестного состояния
```

Не считать мелкие колебания/ошибочные отметки новой поставкой.

Полезно потребовать подтверждение `available` как минимум двумя последовательными poll или достаточным уровнем доверия источника.

Все thresholds вынести в настройки или отдельные constants/config.

Показывать комментарии в UI как дополнительную информацию.

## 11. Прогнозирование

Нужен отдельный forecasting service.

НЕ использовать LLM и не добавлять тяжёлый ML.

На небольшом количестве истории лучше прозрачная статистическая модель.

Прогноз строить отдельно для каждой комбинации:

```text
station + fuel
```

То есть 95, 98 и 100 на одной АЗС имеют независимую историю.

### Этап 1 — мало данных

0–1 подтверждённая поставка:

```text
Недостаточно данных для прогноза
Собираем статистику
```

Не придумывать прогноз.

После 2–3 событий можно показывать грубый прогноз с низкой уверенностью.

### Базовые признаки

Использовать как минимум:

* время суток предыдущих поставок;
* интервалы между поставками;
* день недели;
* количество исторических событий;
* давность истории;
* разброс времени поставок;
* последний момент наличия/отсутствия;
* качество детектированных delivery events.

Статистику делать устойчивой к выбросам.

Предпочтительно:

* median;
* quantiles;
* MAD;
* weighted median / recency weighting.

Не полагаться только на обычное mean/std.

### Пример baseline

Есть события:

```text
10.09 17:21
11.09 18:03
12.09 16:48
13.09 17:36
14.09 17:46
```

Прогноз может получиться:

```text
ожидаемое время: 17:35
диапазон: 16:45–18:30
confidence: 0.72
```

Точные формулы выбери сам и документируй в коде.

Главное:

* результат должен быть воспроизводимым;
* должен быть unit-testable;
* модель должна объяснять результат;
* не выдавать ложную точность.

## 12. Корреляция между АЗС одной сети

Это одна из основных функций.

Например у нас несколько Teboil:

```text
Кронштадтская пл., 4
Ленинский пр., 102
Ветеранов, 188/1
```

Нужно анализировать delivery events одной марки топлива на станциях одного бренда.

Допустим история неоднократно выглядит:

```text
Кронштадтская 15:10
Ленинский     15:47
Ветеранов     16:31
```

и в другие дни последовательность повторяется.

Сервис должен автоматически обнаруживать устойчивый lag:

```text
Кронштадтская
     ↓ ~39 минут
Ленинский
     ↓ ~44 минуты
Ветеранов
```

Не утверждать, что это физически один и тот же бензовоз.

Мы можем говорить только:

```text
исторически после события на АЗС A
событие на АЗС B возникает через X минут
```

Для каждой пары:

```text
brand
fuel
station_from
station_to
```

искать совпадающие события внутри разумного временного окна, например 4–6 часов.

Считать:

* number_of_matches;
* median_lag_minutes;
* MAD/разброс;
* процент случаев, где порядок повторялся;
* давность наблюдений.

Не использовать correlation signal при 1 случайном совпадении.

Например:

```text
minimum matches = 3
```

с низкой уверенностью,

а после 5+ совпадений давать сигналу больший вес.

## 13. Динамический прогноз по соседней АЗС

Если обычный baseline говорит:

```text
Ветеранов:
17:00–21:00
confidence 0.55
```

а только что произошло событие:

```text
Кронштадтская:
АИ-95 появился в 18:07
```

и историческая модель говорит:

```text
Кронштадтская -> Ветеранов
median lag = 83 минуты
MAD = 9 минут
matches = 7
```

нужно пересчитать прогноз:

```text
Ветеранов

ожидается:
19:30

диапазон:
19:15–19:48

confidence:
0.84
```

И сохранить объяснение:

```json
{
  "baseline": "...",
  "cross_station_signal": {
    "source_station": "...",
    "event_at": "...",
    "median_lag_minutes": 83,
    "samples": 7
  }
}
```

Это объяснение использовать в UI.

## 14. Confidence прогноза

Не выводить произвольное красивое число.

Сделать понятную формулу/скоринг на основании:

* количества событий;
* стабильности интервалов;
* стабильности времени суток;
* свежести данных;
* confidence исходных observations;
* качества delivery events;
* количества совпадений между станциями;
* разброса lag;
* наличия свежего события на связанной АЗС.

Результат нормализовать в 0..1 или 0..100%.

В коде должна быть возможность понять, почему получилось именно такое значение.

* при удалении предпочтительно soft delete / disabled;

## 22. Индексы и объём БД

Poll каждые 5 минут:


Но всё равно сделать индексы минимум для частых запросов:

```text

generated_at
```

При необходимости добавить retention/compression позже.

Не делать premature optimization.

## 23. Дедупликация наблюдений

Подумай, нужно ли писать полностью одинаковую строку каждые 5 минут.

Предпочтительный вариант:

история должна позволять понять, что состояние оставалось неизменным и когда сервис реально опрашивал API.

Можно:

* хранить каждый poll;
* либо хранить state changes + heartbeat/snapshot.

Для нашего небольшого количества станций хранение каждого poll допустимо и сильно упрощает аналитику.

Выбери надёжный вариант.

Главное — избежать дублей из-за retry одного и того же poll.

## 32. Что проверить перед завершением

В конце самостоятельно проверь сценарий:

```text
1. Я открываю вкладку «Бензин».
2. Нажимаю «Добавить АЗС».
3. Ввожу адрес.
4. Получаю реальные варианты АЗС рядом.

8. Background collector начинает собирать историю независимо от браузера.

12. После накопления достаточного количества событий появляется forecast.
13. При появлении поставки на связанной АЗС того же бренда forecast пересчитывается.

15. После рестарта контейнеров история не теряется.
```

## 33. Важный принцип

Главная ценность этой функции — НАША накопленная история.

GdeBenz используется как источник текущих наблюдений, но:

```text
история поставок
корреляции между АЗС
прогнозы
confidence
```

должны вычисляться и храниться нашим приложением.

Даже если внешний API завтра изменится, уже накопленная история должна остаться пригодной для анализа.
